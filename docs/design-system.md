# Design System — Material 3 on shadcn

How the M3 design system is put together, and how to finish rolling it out.

Audience: whoever is next in `src/components/`. Read this before restyling
anything.

---

## Why this shape

The constraint was to keep shadcn's architecture (components copied into the
repo, Radix primitives, CVA variants, Tailwind utilities) while replacing the
visual and interaction language wholesale. That rules out MUI and
`@material/web` — both bring their own component model, and `@material/web`'s
Lit custom elements would fight React 19 Server Components at every boundary.

So: **M3 as a token layer plus rewritten component internals.** The public API
of every component stays a shadcn-shaped React component.

The migration leans on one observation. At the start of this work the codebase
had ~1,100 Tailwind call sites reading the shadcn token names —
437 `text-muted-foreground`, 165 `rounded-md`, 291 `text-sm`, `Button` imported
in 149 files. Rewriting those by hand is where a migration like this dies.
Instead, the *token names stay* and their *values* are re-pointed at M3 roles.
Colour, shape and elevation flip for the whole app in one commit; components
then migrate one at a time behind that, and nothing looks broken in between.

## Layer cake

```
src/styles/m3/
  palette.generated.css   (1) ref   — tonal palettes, GENERATED, gitignored
  roles.css               (2) sys   — semantic roles + (3) component tokens
  variants.css                      — @custom-variant for field states
  typography.css                    — @theme --text-* (15 M3 roles)
  shape.css                         — @theme --radius-* (M3 scale)
  elevation.css                     — @theme --shadow-level-*
  motion.css                        — easing, durations, ripple keyframes
  state.css                         — @utility state-layer / m3-focus-ring / ripple-host
  index.css                         — import order
```

`src/app/globals.css` imports `index.css`, then maps roles onto Tailwind's
`--color-*` namespace inside `@theme inline`.

**Layer 1 — reference palettes.** Six tonal palettes (primary, secondary,
tertiary, neutral, neutral-variant, error), 28 tones each, as
`--md-ref-primary-40`. Generated by `scripts/build-theme.cjs` from
`NEXT_PUBLIC_PRIMARY_COLOR`. Never read these outside `roles.css`.

**Layer 2 — system roles.** `--md-sys-color-*`, the M3 role names, defined
once for light on `:root` and once for dark on `.dark`. **This is the layer
new code consumes**, as `bg-surface-container-low`, `text-on-surface-variant`,
`border-outline-variant`.

**Layer 3 — alias bridge.** shadcn's original variable names (`--background`,
`--muted-foreground`, `--card`, …) re-pointed at layer 2. Deprecated on
arrival. Its whole job is to let layers 1–2 ship before any component is
touched. Delete it when the last legacy utility is gone.

### Where each shadcn alias landed

| shadcn alias        | M3 role                     | note |
|---------------------|-----------------------------|------|
| `background`        | `surface`                   | |
| `foreground`        | `on-surface`                | |
| `card`              | `surface-container-low`     | an M3 elevated card is tinted, not white |
| `popover`           | `surface-container-high`    | menus, dialogs, popovers all share this |
| `primary`           | `primary`                   | |
| `secondary`         | `secondary-container`       | see the collision note below |
| `muted`             | `surface-container-high`    | |
| `muted-foreground`  | `on-surface-variant`        | exact semantic match, 437 call sites |
| `accent`            | `surface-container-highest`  | shadcn's hover tint; M3 does this with a state layer |
| `destructive`       | `error`                     | |
| `border`            | `outline-variant`           | |
| `input`             | `outline`                   | M3 text-field borders are `outline`, not `outline-variant` |
| `ring`              | `primary`                   | |

**One name collided.** shadcn's `secondary` was a quiet filled *surface*; M3's
`secondary` is a tone-40 *accent*. The codemod rewrote every shadcn
`bg-secondary` to `bg-secondary-container`, so `secondary` now means what M3
means by it.

### Custom colours: success and warning

The baseline M3 scheme has a role for "wrong" (`error`) and none for "went
well" or "needs attention" — which a records UI needs constantly. M3 supports
*custom colours* explicitly, so `success` and `warning` are generated as full
tonal palettes with the same role shape as error:
`success` / `on-success` / `success-container` / `on-success-container`.

They are seeded from fixed hues rather than the church's colour: "this went
well" has to stay green regardless of branding. These replaced 12 hardcoded
`emerald-*` / `amber-*` utilities that ignored the theme and inverted badly in
dark mode. There are now **zero** hardcoded Tailwind palette colours in `src/`.

## Tokens: decisions worth knowing

### Two knobs: accent scheme and surface tint

M3 colour is an algorithm, not a palette, and this repo drives it with two
independent variables:

```bash
NEXT_PUBLIC_PRIMARY_COLOR=#0F766E      # the seed
NEXT_PUBLIC_M3_SCHEME=tonalspot        # accents
NEXT_PUBLIC_M3_SURFACE_TINT=tinted     # every surface
```

They were **one** knob first, and that was the wrong shape. The goal was
visibly brand-tinted surfaces — the thing that makes an M3 app look like one
system rather than grey boxes with coloured buttons. Surfaces are tones of the
*neutral* palette, so the tint strength is that palette's chroma, and
`SchemeVibrant` raises it from 6 to 10. But the same scheme also maxes the
*primary* palette's chroma (200), and `primary-container` — a large quiet fill
behind text — came out near-neon cyan on a teal seed. Calm accents and tinted
surfaces pull in opposite directions, so they get separate controls:

| `M3_SCHEME` | effect |
|---|---|
| `tonalspot` (default) | M3's own default; restrained accents |
| `vibrant` | maximal accent chroma |
| `expressive` | rotates primary off the seed |
| `content` / `fidelity` | preserve the seed literally |
| `neutral` / `monochrome` | progressively desaturated |

| `M3_SURFACE_TINT` | neutral / variant chroma | look |
|---|---|---|
| `subtle` | 6 / 8 | M3 default; surfaces read near-grey |
| `tinted` (default) | 10 / 12 | surfaces visibly carry the brand hue |
| `vivid` | 16 / 24 | unmistakably coloured surfaces |

On the `#0F766E` seed that lands surfaces at `#eefcf9` / `#e8f7f3` / `#e2f1ee`
and `primary-container` at a soft `#9df2e7` instead of `#00fdec`.

### Colour is generated, not authored

M3 colour is an algorithm, not a palette. Five tonal palettes derive from one
seed hue; every role is a tone of one of them. `scripts/build-theme.cjs` does
that derivation, which buys three things: a per-church rebrand is one env var,
`NEXT_PUBLIC_PRIMARY_COLOR` finally drives the UI instead of only the PWA
manifest, and dynamic colour later is the same code path with a different seed.

Output is gitignored and regenerated on `postinstall`, `predev` and `prebuild`,
exactly like `public/sw.js`. It is per-deployment output, not source.

**Two engines.** The script prefers `@material/material-color-utilities` and
falls back to built-in CIELCh maths if it cannot be loaded.

`@material/material-color-utilities` is **pinned to 0.3.0**. 0.4.0 ships
extensionless internal ESM specifiers (`./dynamiccolor/dynamic_color`) which
Node's ESM resolver rejects, so it only loads inside a bundler. It is also
loaded with dynamic `import()`, not `require()` — the package is pure ESM.

The fallback keeps *tone* exact (tone is CIE L\*, so every contrast
relationship in the spec holds) and approximates *chroma*, because HCT chroma
is CAM16 M and diverges from Lab C by a hue-dependent amount. That divergence
is **not always cosmetic**: at high lightness on cyan-ish hues sRGB permits
enormous Lab chroma, and on this deployment's teal seed (`#0F766E`) the
fallback rendered `primary-90` as near-neon `#00fdec` instead of the correct
`#72f7ea` — unusable as a container role. Treat the fallback as a
build-doesn't-break measure, not as a shipping palette.

**The generator reads `.env.local` itself.** A plain `node` script sees none of
Next.js's dotenv loading, so `pnpm predev` would otherwise have generated the
palette from the fallback seed locally while Vercel (where the variable is set
for real) got the right one. Precedence matches Next: real environment
variable, then `.env.local`, then `.env`.

### `on-*-container` uses tone 10/90, not 30/70

The 2024 spec revision relaxed these. We kept the higher-contrast originals.
This app's audience skews elderly — the PIN throttling is deliberately lenient
for the same reason — and legibility beats fidelity here.

### Typography is additive, not a re-point

Tailwind's default `text-xs` / `text-sm` / `text-base` are 12/16, 14/20 and
16/24 — byte-identical to M3 `body-small` / `body-medium` / `body-large`. So
the 500+ existing call sites needed no change at all. The 15 M3 roles are added
alongside as `text-title-md`, `text-headline-lg`, etc., each carrying size,
line-height, weight and tracking in one utility.

Weights are set on role names only, never on the legacy sizes. Tailwind v4
emits `font-weight: var(--tw-font-weight, <role default>)`, so a `font-*`
utility does still win — but leaving `text-sm` weightless keeps the very common
`text-sm font-semibold` pattern obviously correct rather than
subtly-correct-by-mechanism.

Typeface is **Roboto** (static 400/500/700), not Roboto Flex. The scale only
needs 400 and 500, and this is a PWA on Indonesian mobile networks — three
subsetted woff2 files beat one multi-axis variable font. Roboto Flex is the
upgrade if M3 Expressive's weight-axis animation is ever wanted.

### Shape and elevation *are* re-points

Shape: `rounded-md` 8px → 12px, `rounded-lg` 10px → 16px, `rounded-xl` 14px →
28px. That moved every existing call site onto M3 shape for free. `rounded-xl`
jumps hardest but had only 4 call sites.

Elevation is **tonal first**. Resting surfaces — cards, the nav drawer, sheets,
inputs, tables — are level 0. Only things that overlay unrelated content keep a
shadow: menus, dialogs, FABs, snackbars. Without *some* separation a menu
opened over a card is 92-on-94 tone and effectively invisible.

The shadows that remain are about a third of M3's published opacity. M3's
values are a two-layer recipe at 30% and 15% black, which is what makes a
"Material" implementation look like 2015 Material Design rather than M3.

One switch, on `<html>`, and no component reads it directly:

| `data-elevation` | effect |
|---|---|
| *(unset)* | soft shadows on overlays only — default |
| `flat` | every level is `none`; tone carries everything |
| `material` | M3's published (heavy) values |

### Motion is springs, not curves

M3's current motion system is **spring physics**. The duration + cubic-bezier
tier still exists and is still spec'd, but it is the legacy one, and no
cubic-bezier can express a spring at all — a cubic-bezier's output is bounded
by its endpoints, and overshoot is most of what makes M3 motion read as M3.

CSS `linear()` can overshoot, because it takes sampled output values and those
values may exceed 1. So [`scripts/build-motion.cjs`](../scripts/build-motion.cjs)
integrates the spring ODE and emits `linear()` easings plus their settle
durations into `src/styles/m3/spring.css`.

Exact token values come from the Android source of truth
(`StandardMotionTokens.kt` / `ExpressiveMotionTokens.kt`):

| token | standard (damping / stiffness) | expressive | peak |
|---|---|---|---|
| default-spatial | 0.9 / 700 | 0.8 / 380 | 1.015 |
| fast-spatial | 0.9 / 1400 | 0.6 / 800 | **1.095** |
| slow-spatial | 0.9 / 300 | 0.8 / 200 | 1.015 |
| default-effects | 1.0 / 1600 | 1.0 / 1600 | 1.000 |
| fast-effects | 1.0 / 3800 | 1.0 / 3800 | 1.000 |
| slow-effects | 1.0 / 800 | 1.0 / 800 | 1.000 |

**The rule that matters: spatial may overshoot, effects never do.** Position,
size and corner radius get spatial springs. Opacity and colour get effects
springs, which are critically damped — a bouncing opacity reads as a rendering
fault, not as liveliness.

Expressive is the default; `<html data-motion="standard">` opts into the calmer
scheme. Under `prefers-reduced-motion` every spring collapses to 1ms linear.

Use the paired utilities — `motion-spatial`, `motion-spatial-fast`,
`motion-effects-fast` — rather than an easing and a duration separately. A
spring's duration is a property of its physics; splitting them across two
utilities is how a bouncy curve ends up crammed into 150ms.

### Enter/exit transitions

`tw-animate-css`'s `animate-in fade-in-0 zoom-in-95` cannot be used for M3
motion, because it composes opacity and transform into **one** keyframe
animation, which can carry only one easing. Either the scale loses its bounce
or the opacity gains one.

CSS allows a comma-separated animation list, so
[`transitions.css`](../src/styles/m3/transitions.css) gives each property its
own spring:

| utility | used by | motion |
|---|---|---|
| `m3-menu-enter` | menu, select, dropdown | `scaleY(0.75)→1` spatial + opacity effects |
| `m3-dialog-enter` | dialog, popover, tooltip | `scale(0.9)→1` spatial + opacity effects |
| `m3-scrim-enter` | dialog/sheet scrims | opacity only |

Menus grow along their major axis from Radix's reported transform origin, not
uniformly — that is what makes a menu look like it unfolds out of its trigger
rather than appearing over it. Exits are deliberately *not* springs: things
leave fast and do not overshoot, or the surface looks reluctant to close.

### Transition patterns

M3 defines four, and which one applies is a statement about the **relationship
between two screens**, not a style choice:

| pattern | relationship | status |
|---|---|---|
| **fade** | enters/exits within the screen — dialog, menu, tooltip | done |
| **fade through** | destinations with no strong relationship — top-level nav | done, incoming half |
| **shared axis** | spatial/navigational — list → detail, back | done, incoming half |
| **container transform** | a container morphs into the destination | **done** |

`PageTransition` picks between the middle two from route depth — the only
signal available without annotating every link, and in this app's URL shape it
encodes exactly the right distinction. Deeper is forward, shallower is
backward, equal depth is a fade through. The choice lives in
[`src/lib/transition-pattern.ts`](../src/lib/transition-pattern.ts) as a pure
function with unit tests, because it is the part that can actually be wrong —
and it was: the first version compared pathnames as raw strings, so
`/me/events/` → `/me/events` counted as a navigation and animated a fade for a
route that had not changed.

Keyed on pathname, so search-param changes deliberately do **not** animate. A
filter or a page number is not a navigation, and animating one makes table
filtering feel slow.

**Only the incoming half.** M3's fade-through is sequential — the outgoing
screen fades over the first ~30% of the duration — but React unmounts the old
tree before the new one commits. Holding it means intercepting every
navigation and delaying it ~90ms, which pays real latency on every tap to
render a fade.

**Container transform is implemented** at two complementary layers:
1. **Component-level `<ContainerTransform>`** ([`src/components/m3/container-transform.tsx`](../src/components/m3/container-transform.tsx)):
   Uses the FLIP (First, Last, Invert, Play) technique powered by M3's physics-based spatial spring (`--md-sys-motion-spring-default-spatial`) to morph compact containers (cards, FABs) into expanded dialogs/sheets and back with true overshoot and reversible motion.
2. **CSS View Transitions API**:
   Standard M3 pseudo-elements (`::view-transition-group(m3-container)`, `::view-transition-old`, `::view-transition-new`) are defined in [`transitions.css`](../src/styles/m3/transitions.css) with spatial and effects spring timing functions for progressive enhancement across browser-native view transitions.


### A note on where these numbers came from

`m3.material.io` is a client-rendered SPA and returns only a page title to any
fetch, so the spec pages cannot be read programmatically. Everything here was
taken from the implementations Google generates *from* those specs:
`StandardMotionTokens.kt` / `ExpressiveMotionTokens.kt` for the spring
constants, and `material-components-android/docs/theming/Motion.md` for the
transition patterns.

One trap in that second source: its published durations and easings
(`motionEasingStandard` = `cubic-bezier(0.4, 0, 0.2, 1)`, container transform
at 300ms) are **M2-era** values. The patterns and their semantics carry over to
M3; the timings do not. The spring tier supersedes them here.

### The tab indicator slides

The first version gave every trigger its own `::after` and cross-faded their
opacity, so the indicator **popped** between tabs. In M3 it travels, and that
travel is most of what makes a tab row feel like M3.

A pseudo-element cannot animate between two elements, so there is exactly one
indicator, positioned from the active trigger's measured box and moved on a
spatial spring. Measurement is driven by a MutationObserver on `data-state`
(Radix's own signal) plus a ResizeObserver for reflow and web-font swap.

Primary and secondary measure **different boxes**: secondary spans the whole
tab; primary hugs the *label*, measured with a `Range` over the trigger's
contents. With `flex-1` triggers those differ by several times — insetting the
tab box by a fixed amount gives a bar far wider than its text, which was the
first thing that looked wrong once it was on screen.

The indicator is client-only (it needs layout before it can be placed), so it
is absent from the server HTML and appears on hydration; a `ready` flag
suppresses the transition for that first placement.

## Shape

Three parts to M3 shape, and only the first is a token problem.

**Shape scale** — the radius tokens above. Done.

**Shape morph** — M3 Expressive treats shape as a *state*: press a component
and its corners move. `border-radius` is spatial, so it takes a spatial spring
and is allowed to overshoot; that slight overshoot is what makes a corner feel
like it has mass rather than like a value being reassigned. The rule, where it
is used: **on press, step the radius down one level of the shape scale.** M3
publishes the morph behaviour but not per-component web tokens for the target
shapes, so the target is an interpretation, and the direction (tighter under
the finger) matches M3 Expressive's own button demos.

**Now applied to interactive cards and quick-action tiles only.** It was
removed from `Button` and `Toggle` on request. On a `rounded-full` control the
morph is a pill snapping to a rounded rectangle and back on every click, and
across a form full of buttons that reads as the UI glitching rather than as the
button acknowledging the press — the state layer and the elevation step already
carry the press without moving the geometry. The `shape-morph` and
`shape-morph-interactive` utilities are unchanged and still in use; the two
components just dropped `active:rounded-md`, and their transition lists moved
from the combined `shape-morph-interactive` to `motion-effects-fast` plus an
explicit property list, since they no longer transition `border-radius`.
Reduced motion is still covered either way — `spring.css` zeroes every spring
duration token at the root, not per utility.

**Shape library** — M3 Expressive ships ~35 named polygon shapes (clover,
burst, sunny, gem, pentagon, puffy…). **Not implemented**, deliberately. They
are rounded polygons, and CSS has no scalable primitive for one:
`clip-path: polygon()` scales but has sharp corners, `clip-path: path()` keeps
the rounding but is in fixed px and does not scale with the element. A faithful
port means generating SVG masks from the polygon geometry — a real project,
for shapes that appear nowhere in this app's screens and nowhere in the
reference design that prompted this work. The seam if it is ever wanted: a
`shape-*` utility family backed by SVG `mask-image`, sitting beside
`shape-morph`.

## State layers: the part that isn't cosmetic

This is the biggest behavioural gap between shadcn and M3, and the reason a
pure token swap doesn't get you Material.

shadcn expresses interaction by changing the container colour
(`hover:bg-primary/90`). That needs a bespoke rule per variant, and does
nothing at all on transparent variants — a shadcn ghost button gets its hover
from `bg-accent`, which is a different mechanism again.

M3 overlays a translucent layer of the **content** colour at fixed opacities:
8% hover, 10% focus, 10% press, 16% drag. `@utility state-layer` implements
that as a `::before` painted with `currentColor`, which turns out to be exactly
right everywhere with no configuration:

| surface | `currentColor` | resulting wash |
|---|---|---|
| filled button | `on-primary` | white over primary |
| tonal button | `on-secondary-container` | dark over tonal |
| text / outlined | `primary` | primary over nothing |
| card, list row | `on-surface` | ink over surface |

Two mechanics to preserve if you touch it:

- `isolation: isolate` on the host + `z-index: -1` on the pseudo-element is
  what keeps the wash above the host's own background but below its text and
  icons. Without the isolation, the negative z-index escapes to the nearest
  ancestor stacking context and the wash vanishes behind the page.
- **`::before` is the state layer. `::after` is free** (Tabs uses it for the
  active indicator). Don't cross them.

Override `--md-state-layer-color` when the content colour isn't the right wash.

### Focus and disabled

Focus is a 3px `secondary` outline offset 2px, as `@utility m3-focus-ring`,
plus a global `:focus-visible` fallback in `globals.css` so un-migrated
components still get the right indicator. Deliberately `outline` rather than
`box-shadow`: an outline isn't clipped by the `overflow: hidden` that ripple
containment needs, and it survives forced-colors mode.

Disabled is per-element — container at `on-surface/12`, content at
`on-surface/38` — not `opacity-50`. Blanket opacity also fades the container's
contrast against the page, so a disabled filled button and a disabled text
button stop reading as the same kind of thing.

### The ripple is opt-in, on purpose

The press ripple needs press coordinates, so it can't be CSS. Baking it into
`Button` would force `"use client"` onto a component imported by ~150 files,
most of them Server Components, dragging the client boundary up with it. That
is a real bundle and streaming cost for a decorative flourish.

So `Button` ships CSS state layers only, and `@/components/m3/ripple` is
composed into surfaces where the press origin actually carries meaning — nav
items, list rows, FABs, calendar days, all already client components:

```tsx
<button className="ripple-host state-layer rounded-full">
  <Ripple />
  <Icon />
</button>
```

It binds to `parentElement`, the same contract `<md-ripple>` uses, and
no-ops under `prefers-reduced-motion`.

## Components

Everything in `src/components/ui/` is migrated. `src/components/m3/` holds the
three components that have no shadcn counterpart.

| Component | M3 mapping | Note worth knowing |
|---|---|---|
| `button` | button + FAB | 5 variants; shadcn names aliased; FAB variant + size |
| `card` | card | elevated / filled / outlined, `interactive`, `density` |
| `dialog`, `alert-dialog` | basic dialog | `surface-container-high`, 28dp, level 3; actions default to text buttons |
| `text-field` (m3) | text field | outlined + filled, notched floating label |
| `input`, `textarea` | text field body | 56dp; `density="compact"` gives 40dp |
| `select` | select | trigger is a text field, list is a menu |
| `dropdown-menu` | menu | **48dp items** — the largest density change in the migration |
| `checkbox` | checkbox | 18dp box with the 40dp overhanging state layer |
| `toggle` / `toggle-group` | toggle button / segmented button | shared outline, round ends |
| `tabs` | primary + secondary tabs | 3dp / 2dp indicators |
| `navigation` (m3) | nav bar / rail / drawer | selection is a shaped container |
| `sidebar` | navigation drawer + rail | shadcn shell kept, items are M3; 360dp / 80dp |
| `table` | list rules | 56dp head, 52dp rows, `on-surface/8` hover |
| `badge` | between badge and chip | 24dp status pill; see note below |
| `alert` | (none) | container role pairs; M3 has no inline alert |
| `tooltip` | plain tooltip | `inverse-surface`, **no arrow** |
| `sonner` | snackbar | `inverse-surface`, 4dp shape |
| `calendar` | date picker | 40dp circular days; today is an outline, not a fill |
| `chart` | (none) | recharts chrome re-pointed at roles; tooltip is inverse |
| `avatar` | avatar | `primary-container` monogram |
| `breadcrumb`, `separator`, `skeleton`, `label`, `form`, `popover`, `sheet`, `drawer`, `input-otp` | various | see each file's header comment |

A few of these are judgement calls rather than spec lookups:

- **`badge`** — M3 has a *badge* (a 16dp `error` dot on an icon) and a *chip*
  (32dp, interactive). This component is used as a non-interactive status pill
  in table rows, which is neither, so it sits between them at 24dp. Its
  `default` also moved from solid `primary` to `secondary-container`: a small
  pill filled with `primary` is very loud in M3's colour system, and status
  pills are ambient information. `variant="primary"` is there when a badge
  genuinely needs to shout. It carries **12dp** of horizontal padding, which is
  its corner radius: on a `rounded-full` box the radius is half the height, so
  padding below that puts the first glyph inside the curve and the label looks
  like it is touching the border. This was on 8dp and looked cramped wherever
  `variant="outline"` made the border visible. Same ratio M3 gives its 32dp
  chip (16dp padding, 16dp radius). Resize a pill, move its padding — and note
  the exemption: `Button`'s text/ghost variants sit at 12dp on a 40dp pill
  because they have no resting container for the curve to show on.
- **`tooltip`** — the arrow is gone. M3 tooltips have no caret; the inverse
  surface is what makes them read as a layer above the page. An arrow is the
  clearest giveaway of a Material-flavoured tooltip that isn't following the
  spec.
- **`table`** — row hover is the M3 state layer expressed as a background
  (`on-surface/8`, the exact value `state-layer` uses) rather than a
  pseudo-element. `<tr>` is a poor host for an absolutely-positioned
  `::before` because its box model varies with `border-collapse`, and a
  background composites identically here since a row has no shape of its own.
- **`sidebar`** — the shadcn shell (collapse logic, mobile sheet, keyboard
  shortcut, rail) is worth keeping; only the item styling changed. Widths moved
  to M3's 360dp drawer / 80dp rail, and the active state became a full-width
  28dp `secondary-container` pill. Previously `data-[active=true]` was a faint
  grey tint indistinguishable from hover.

### Sizes and density

`Button` is 40dp by default (M3), was 36dp. `xs` is 32dp (M3 Expressive
extra-small) and is the floor for anything tappable.

**One documented deviation:** `sm` is 36dp. M3 offers no 36 step, and moving the
~40 existing `size="sm"` call sites to 40dp costs a visible row in the admin
data tables. Density in a records-management UI is a real requirement, so `sm`
keeps 36 and the deviation is written down rather than silently absorbed.

`Card` padding drops 24dp → 16dp (M3). `density="spacious"` restores 24dp for
screens whose layout was designed around it.

### Text field: why a new component, and why a `<fieldset>`

M3's text field isn't a styled input — the label lives inside the control and
animates into the outline. Different DOM, different API, so `ui/input.tsx`
stays for bare controls (search bars, table filters, OTP/PIN).

Breaking the outline where the floated label crosses it has three options:
give the label a matching background (a lie — breaks on any surface tone you
didn't predict, and M3 fields sit on several); split the border and size the
gap in JS (what `material-web` does — pixel-perfect, needs a ResizeObserver);
or a real `<fieldset>` + `<legend>` holding a copy of the label, where the
browser breaks the border for free.

`<fieldset>` wins **here specifically because the app is bilingual**: "Nomor
telepon" and "Phone number" are different widths and next-intl can swap them
without a remount. A JS-measured notch would have to re-measure; a legend just
reflows.

Label float is CSS-only via `placeholder=" "` + `:placeholder-shown`, so it
works with uncontrolled RHF `register()`, with controlled values, and with
browser autofill, without an effect. The four `field-*` custom variants in
`variants.css` exist because the label and the legend need to react to the
*input's* state and are not its previous siblings — Tailwind's `peer-*` can't
express that.

### Navigation

What makes navigation read as M3 is not colour, it is that selection is a
**shaped container** behind the icon — 64×32 pill in the bar, 56×32 in the
rail, full-width 28dp pill in the drawer — filled with `secondary-container`.

This is why the existing `member/mobile-bottom-nav.tsx` doesn't read as
Material despite being a nice component: a floating glassmorphic pill with a
colour-only active state is a different design language, and no token swap
converts it. Replacing it with `NavigationBar` is a deliberate design
decision, not a refactor — make it consciously.

**Icons are the one place lucide costs fidelity.** M3 swaps outlined → filled
icons on selection; lucide has no filled variants. `NavDestination.activeIcon`
is the seam: pass a filled equivalent where lucide has one, otherwise the
indicator pill and label weight carry the state. Adding Material Symbols as a
second icon font for navigation alone isn't worth the payload on a PWA, but
`activeIcon` is where it would land if that changes.

## Traps this migration hit

Four bugs that were invisible — no error, no failed build, no failed test — and
that any Tailwind design system with custom tokens will hit in the same way.

### `cn()` silently deletes custom type roles

`tailwind-merge` resolves conflicts by bucketing each class into a group, and
it only knows Tailwind's **default** size scale. A custom `--text-*` key like
`text-title-lg` is unrecognised, so it falls through to the `text-color`
group — the same group as `text-on-surface` — and

```ts
cn("text-title-lg text-on-surface")   // -> "text-on-surface"
```

returns only the colour. Every card title, dialog headline and badge label lost
its size, and the page still rendered fine: 53 of the 105 type-role call sites
pair a role with a colour in one string. Found by reading the served HTML, not
by any tool.

The fix is in [`src/lib/utils.ts`](../src/lib/utils.ts): register the 15 type
roles under `font-size` and the elevation levels under `shadow` via
`extendTailwindMerge`. **A design system that adds `@theme` keys owes
tailwind-merge a matching class group.**

### `@custom-variant` wrapped in `:where()` has zero specificity

The four `field-*` variants copied the `dark` variant's shape:

```css
@custom-variant field-populated (&:is(:where(.m3-field:has(...)) *));
```

`:where()` contributes zero specificity and `:is(:where(X) *)` inherits that
zero, so `field-populated:max-w-full` tied with the base `max-w-[0.01px]` at
(0,1,0) and lost on source order. The text field's notched outline never
opened; the label floated but the border drew through it, which looked exactly
like a strikethrough. Dropping `:where()` puts the variants at (0,3,0).

Tailwind's `--tw-*` fallback trick — which is what lets `font-semibold`
override a type role's weight — exists for only a handful of properties.
For `top`, `max-width` or `border-width`, specificity is the only lever.

### The notch and the label were positioned by different mechanisms

Same component, separate bug. The floated label is positioned absolutely; the
notch is positioned by the *fieldset's* padding. With a leading icon the label
moved to 52dp and the notch stayed at 8dp. Both now derive from one
`--field-inset` variable set on the field root. Any time two elements have to
align pixel-for-pixel, give them one source of truth rather than two matching
literals.

### Dark mode never existed

`next-themes` was a dependency, `ui/sonner.tsx` already called `useTheme()`,
and no `ThemeProvider` was ever mounted — so the `.dark` class never landed on
`<html>`. Every `.dark` role was unreachable. Now mounted in
[`theme-provider.tsx`](../src/components/shared/theme-provider.tsx) with
`attribute="class"`, matching the `@custom-variant dark` in globals.css.

## Charts

The three charts in the app are wired to `--chart-1..5`, which are **not** tones
of the tonal palettes. The obvious `chart-1 = primary-40` was tried and fails a
measurable gate: at `#006a63` the OKLCH chroma is 0.082, below the 0.1 floor
where a mark stops reading as coloured. M3 accent roles are tuned for large
areas and text, where restraint is right; a 4px bar segment needs more chroma
than a button fill.

Slot 1 is therefore the brand hue re-stepped (`#0f8f7a`), and the rest alternate
warm/cool so adjacent pairs survive colour-vision deficiency. Both modes are
validated against the card surface each actually uses — not eyeballed:

| mode | surface | result |
|---|---|---|
| light | `#e8f7f3` | 5 slots pass adjacent; worst CVD ΔE 11.2, normal-vision 19.6 |
| light | | first 3 pass all-pairs, every slot ≥ 3:1 contrast |
| dark | `#111e1c` | 5 slots pass everything, all ≥ 3:1 |

Assign slots in fixed order and never cycle; a sixth series folds into "Other"
or becomes small multiples. Slots 4–5 sit below 3:1 on the light surface, so a
chart reaching them owes the reader visible labels or a table view.

**Known defect, not yet fixed:**
[`membership-growth-chart.tsx`](../src/components/admin/reports/membership-growth-chart.tsx)
is a dual-axis chart — `joined` on a left scale, `cumulative` on a right one.
Two y-scales make the series visually comparable when they are not, and the
crossover point is an artifact of the scale choice rather than a fact about the
data. The fix is two charts or one indexed to a common base; both change the
reports page layout and its translation keys, so it is left as a decision
rather than folded into a restyle.

## The expressive layout layer

Everything above is a *component* library. This section is the layer above it:
the page-level composition language, which was designed on the member dashboard
and then rolled out to every screen in the app.

It exists because a migrated component library does not by itself produce a
coherent product. After phase 4 every button, card and table was M3, and the
pages were still shadcn pages: an `h1.text-3xl`, a stack of
`Card > CardHeader > CardTitle > CardContent`, and `rounded-md border
border-dashed p-10 text-center` wherever a list came back empty. Same tokens,
different language.

### The seven rules

1. **A block is borderless, tonal and 24dp.** `surface-container-low` on a
   `surface` page, `shadow-level-0`. Tone carries the boundary; nothing gets a
   border unless tone cannot work (a block on an already-tonal region, a text
   field, a quoted verse).
2. **One tonal step, not two.** These blocks are large and repeat down a phone
   screen. Two steps is a wall of grey. One step still separates, and it leaves
   `surface-container` free as the *hover* state — which is how an interactive
   block signals itself without spending a shadow.
3. **Nesting steps up in tone and down in radius.** A row inside a block is
   `surface-container-high` at 16dp. This is the pair that replaced
   `rounded-md border p-3`, and it is the one that survives dark mode — a
   hairline border there turns into a grey scratch.
4. **Every block group is anchored by an icon chip.** A page is a stack of
   large tonal blocks with no rules between them, so the eye needs a hard mark
   to find where one group ends. 28dp for a section heading, 40dp for a block,
   48dp for a hero.
5. **Eyebrow, then title.** M3's "eyebrow + headline" from `ui/card.tsx`,
   lifted to the page: a tracked uppercase `label` in `primary` above the
   screen's name. On a detail page the eyebrow is the *parent record*, which is
   why `PageHeader`'s `backLabel` doubles as the default eyebrow.
6. **Empty is a state, not a failure.** A dashed border says "content failed to
   arrive". A member with no prayer requests yet is not a failure, so an empty
   state is a real tonal block with a promoted icon and a title that says
   something.
7. **Actions are pills.** `Button` is already `rounded-full`; inline actions are
   `size="sm"` at 36dp, page actions 40dp.
8. **The inset has to clear the corner arc.** The app got this wrong in three
   separate places, and the reason it keeps happening is that **the radius scale
   here is not Tailwind's** — `shape.css` re-points it to M3, so `rounded-lg` is
   16dp, `rounded-xl` 28dp, `rounded-2xl` **36dp** and `rounded-3xl` **48dp**.
   The class names read far tamer than the shapes they produce, so an inset
   copied from a stock-Tailwind instinct lands nowhere near the corner it has to
   clear.

   The geometry: content inset by *p* from both edges sits at the corner point
   (*p*,*p*), and the arc's centre is at (*r*,*r*). It clears the curve only
   while *p* > *r*(1 − 1/√2) ≈ **0.29*r***, and the clearance it actually has on
   the diagonal is *r* − √2(*r* − *p*), which is always less than *p*. Keep that
   diagonal at roughly half the edge inset or better; at a fifth it reads as
   wedged into the curve, which is the tell.

   | Shape | Radius | Inset | Diagonal | |
   |---|---|---|---|---|
   | filter bar, before | 36dp | 12dp | 2.1dp | wedged |
   | `StatTile` at `compact`, before | 48dp | 16dp | 2.7dp | wedged |
   | `ExpressiveCard` `nested` + `compact` | 36dp | 16dp | 7.7dp | ok |
   | `ExpressiveCard` 48dp + `compact` | 48dp | 20dp | 8.4dp | ok |
   | `StatTile` at `default` (`sm:`) | 48dp | 24dp | 14.1dp | good |
   | filter bar, after | 16dp | 12dp | 10.3dp | good |

   So: `ExpressiveCard` pairs `padding="compact"` to the tone's radius in
   `compoundVariants` so the two scales cannot drift apart by hand; `StatTile`
   takes the full `default` inset because it is the one shape that parks content
   in all four corners; a filter bar steps *down* to 16dp rather than padding out
   to meet 36dp, because it holds 4dp controls and 36dp was never the right jump
   from them; and a fully-round pill takes horizontal padding equal to half its
   height, since that is its radius. The exemption is a control with no resting
   container — `Button`'s text and ghost variants sit at 12dp on a 40dp pill
   because there is no curve on screen to clear.

### The one documented deviation

**Titles are bold.** `docs/design-system.md` says above that M3 almost never
sets display or headline text bold, and that is still true of the component
library. The page and block *titles* in this layer break it on purpose: these
screens are read on a phone at arm's length with a thumb on a bottom nav bar,
and a `headline-sm` at regular weight loses the top of the hierarchy to the
first tonal block below it — which here is large, 24dp and coloured. Bold at
24/30px is what keeps the title winning. It is not licence to bold headlines
elsewhere.

### The components

All in `src/components/m3/`, all server-safe (no `"use client"`), all visible
together in `/m3` under "Expressive layout".

| Component | Replaces | Note |

### How the rollout was done

Mostly by codemod, because 94 page files is where a migration like this dies by
hand. Three passes, each one structural rather than textual, and each bailing
out of anything it did not fully understand so the irregular pages got read
instead of half-converted:

1. **Headers.** Two uniform `<header>` shapes, then the back-button variants,
   then 9 rich detail headers by hand. `<PageHeader>` for all 94 screens.
2. **Blocks.** `Card` → `BlockSection` (54) or `ExpressiveCard` (15), matching a
   `</Card>` to the `<Card>` at its own indentation. An icon inside a
   `CardTitle` is lifted into `BlockSection`'s `icon` slot.
3. **Shapes.** `rounded-md border` retired token by token inside className
   literals: padded boxes became 16dp rows, unpadded ones 24dp shells, and a box
   naming a border *colour* was left outlined because it is a control.

Two lessons worth keeping. The codemod must forward **every** attribute it does
not understand — the first version dropped `key` on five list items, which
typecheck could not see and only `react/jsx-key` caught. And re-indenting JSX
with a regex compounds: each pass re-measured indentation the previous pass had
already changed, so the fix was to `git checkout` the tree and re-run one
correct pass, not to patch the patches.

### If you add a screen

- `PageHeader` at the top. Eyebrow from the `eyebrow.*` namespace on a module
  screen; `backHref` + `backLabel` on a detail screen, and let the label become
  the eyebrow.
- Blocks are `BlockSection` (titled) or `ExpressiveCard` (untitled). Rows inside
  them are `BlockRow`.
- Empty is `EmptyState`, never a dashed border. Notices are `Banner`.
- **Step the densities down when you nest.** A `SectionHeader` inside a
  `BlockSection` needs `size="sm"` — at the default both render `text-base`
  bold and the sub-heading reads as important as the block containing it. An
  `EmptyState` inside such a sub-section needs `size="sm"` too: at full size a
  48dp chip over a bold 16px line makes *absence* the tallest thing on the
  screen. The admin dashboard had four of them and was mostly whitespace.
  `className="py-6"` is not the fix — it trims the padding and leaves the chip
  and the display weight.
- `pb-28 sm:pb-12` on member-portal pages — the mobile bottom nav is fixed and
  will otherwise sit on top of the last block.
- Add a `loading.tsx` whose skeleton uses the *same* shapes
  (`rounded-3xl bg-surface-container-low`), including the eyebrow line.
  `src/components/shared/skeletons/` has them.

## Rollout

All four phases are done. Recorded here because the *order* is the reusable
part — it is what kept the app shippable at every commit.

**Phase 1 — tokens.** Layers 1–3, typography, shape, elevation, motion, state
utilities, Roboto, generator wiring. After this commit the app was fully
M3-coloured and M3-shaped while every component was still shadcn, because the
alias bridge re-pointed the token *values* under ~1,100 untouched call sites.
This is the phase that makes the rest optional rather than urgent.

**Phase 2 — high-traffic primitives.** Button, Card, Dialog, Tabs, TextField,
Navigation. Chosen by call-site count: Button alone is 149 files, so it
converts more surface area than everything else combined.

**Phase 3 — the remaining 26 components in `ui/`.** Each one: legacy alias →
sys role, `state-layer` + `m3-focus-ring` replacing `hover:bg-*` and
`focus-visible:ring-*`, `disabled:opacity-50` → `on-surface/12` + `/38`, type
to role utilities, then added to `/m3`.

**Phase 4 — bridge deleted.** A codemod rewrote 535 utility call sites across
123 files (`text-muted-foreground` → `text-on-surface-variant`, and so on),
the 12 hardcoded `emerald`/`amber` utilities became `success`/`warning` roles,
and layer 3 was reduced to the `--sidebar-*` / `--chart-*` component tokens.
Verified by compiling the stylesheet and asserting that no shadcn alias
variable survives in `:root`.

The codemod is worth understanding before writing another one. It matches
`<prefix>-<token>` as a whole utility with `(?<![\w-])` / `(?![\w-])`
boundaries, which is what makes `dark:`, `hover:` and `/40` modifiers ride
along untouched. Tokens are applied longest-first so `primary-foreground` wins
over `primary`. `text-card-foreground` was never at risk from the `foreground`
rule, because the substring `text-foreground` does not occur in it — matching
whole utilities rather than fragments is the entire trick.

### If you add a component

1. Read the sys roles, never `--md-ref-*`.
2. `state-layer` + `m3-focus-ring` for anything interactive;
   `state-layer-control` for 18–20dp selection controls, which need the 40dp
   overhanging wash to reach a legal touch target.
3. Disabled is `on-surface/12` (container) and `on-surface/38` (content).
4. Type through role utilities (`text-label-lg`, `text-title-sm`).
5. Selection is a *shaped container* in `secondary-container` — not a tint, not
   a colour-only change. This is the single rule that most determines whether
   something reads as Material.
6. Add it to `/m3`.

### Keeping the door open for dynamic colour

Everything needed is in place. Layer 1 is generated from a seed and nothing
above it knows where the seed came from. Three progressively more dynamic
options, none requiring a restructure:

1. **Today** — seed from `NEXT_PUBLIC_PRIMARY_COLOR` at build time.
2. **Per-church runtime theming** — move generation into a Server Component
   that emits `--md-ref-*` into a `<style>` tag from a DB-stored seed. Layer 2
   onward is unchanged.
3. **True M3 dynamic colour** — `sourceColorFromImage` from
   material-color-utilities (already a devDependency) to extract a seed from a
   user-supplied image, emitted client-side. Also unlocks the spec's contrast
   levels and scheme variants (`SchemeTonalSpot`, `SchemeVibrant`, …).

Add a `--md-sys-` role or a `--md-ref-` tone before you need it, not a new
layer.

### Guardrails

- Read sys roles. `--md-ref-*` is private to `roles.css`.
- Never hardcode a colour. If the palette can't carry the semantics, add a
  custom colour to the generator the way `success` and `warning` were added.
- `::before` is the state layer; `::after` is free (Tabs uses it).
- Don't grow a border on focus — a 1dp border plus a 2dp `inset-ring` gives
  M3's 3dp focused outline with no layout shift. Growing the border nudges the
  field's contents 2px.
- Add every new component to `/m3`. A design-system migration stalls when
  nobody can see all the states at once and regressions get found one screen at
  a time, by users.
